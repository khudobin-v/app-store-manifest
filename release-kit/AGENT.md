# Как ИИ-агенту добавить приложение в личный магазин

Инструкция для ИИ-помощника (Claude Code, Codex и т. п.), который работает
**внутри репозитория Android-приложения**. Задача: подключить репозиторий к
личному магазину так, чтобы дальше публикация версии была одной командой
`./release.sh 1.4.0 "Что нового"`.

Читай целиком до начала работы: половина шагов бессмысленна без остальных.

## Что нельзя делать

- **Не вводи и не запрашивай пароли, токены и содержимое keystore.** Секреты
  ставит человек своей рукой. Твоё дело — дать точные команды и проверить, что
  нужные secret'ы существуют (`gh secret list` показывает только имена).
- **Не коммить keystore, `local.properties`, `.env`.** Ключ живёт вне
  репозитория, в GitHub Secrets — только его base64.
- **Не создавай ключ подписи заново для приложения, которое уже публиковалось.**
  Android не поставит обновление, подписанное другим ключом: человеку придётся
  удалять приложение вместе с данными. Если ключ потерян — останови работу и
  скажи об этом прямо.
- **Не понижай и не переиспользуй `versionCode`.** Витрина отклоняет дубликат
  кодом 409, релиз падает.

## Шаг 0. Собери факты о репозитории

Прежде чем что-то менять, выясни и покажи человеку:

```bash
ls app/build.gradle.kts build.gradle.kts settings.gradle.kts 2>/dev/null
grep -nE "applicationId|versionCode|versionName|minSdk|targetSdk" app/build.gradle.kts
gh repo view --json nameWithOwner,visibility -q '.nameWithOwner + " " + .visibility'
gh secret list
```

Проект должен собираться Gradle'ом и иметь модуль `app`. Если это не
Android-приложение (нет `com.android.application`), дальше идти нельзя —
скажи об этом.

## Шаг 1. Скопируй файлы конвейера

Из `release-kit` в репозиторий приложения:

| Из release-kit | Куда |
|---|---|
| `release.sh` | `release.sh`, затем `chmod +x release.sh` |
| `.github/workflows/release.yml` | `.github/workflows/release.yml` |
| `tools/screenshots.sh` | `tools/screenshots.sh`, `chmod +x` |

`store/icon.png` — иконка 512 × 512 для карточки в магазине. Если её нет,
собери из иконки приложения (`app/src/main/res/mipmap-*`) или спроси картинку у
человека. Без неё магазин покажет заглушку с первой буквой названия.

## Шаг 2. Подпись релизной сборки

Вставь в `app/build.gradle.kts` сниппет из
`release-kit/signing-config.gradle.kts.snippet`. Он устроен так, что **локальная
сборка не ломается**: без переменной `KEYSTORE_PATH` конфигурация подписи просто
не создаётся.

Проверь после вставки:

```bash
./gradlew assembleRelease   # должно пройти без ключа
```

## Шаг 3. Версии

В `app/build.gradle.kts`:

- `versionName` обязан совпадать с версией, которую передадут в `release.sh`, —
  конвейер сверяет их и падает при расхождении;
- `versionCode` — целое, растёт на каждый релиз.

Пропиши рядом комментарий, что код версии поднимается на каждый релиз: это
первая причина падений у тех, кто вернётся сюда через полгода.

## Шаг 4. Секреты (делает человек)

Скажи человеку выполнить — сам не запускай, если это потребует ввода пароля:

```bash
./tools/setup-app-repo.sh            # заведёт ключ и четыре KEYSTORE_*-секрета
gh secret set STORE_API              # адрес витрины, https://…vercel.app
gh secret set PUBLISH_TOKEN          # токен публикации из окружения бэкенда
```

Затем проверь сам:

```bash
gh secret list | grep -E "KEYSTORE_BASE64|KEYSTORE_PASSWORD|KEY_ALIAS|KEY_PASSWORD|STORE_API|PUBLISH_TOKEN"
```

Шесть строк — можно продолжать. Меньше — останови работу: релиз упадёт на
сборке или на публикации.

## Шаг 5. Первый релиз

```bash
git add -A && git commit -m "Публикация в личный магазин" && git push
./release.sh 1.0.0 "Первый релиз"
```

`release.sh` только ставит аннотированный тег: сообщение тега становится
changelog'ом в карточке приложения. Всё остальное делает GitHub Actions.

## Шаг 6. Проверь результат, а не «должно работать»

```bash
gh run watch "$(gh run list --limit 1 --json databaseId --jq '.[0].databaseId')" --exit-status
curl -s "$STORE_API/api/apps" | python3 -m json.tool | grep -A3 '"id"'
```

Приложение должно появиться в ответе витрины с нужными `versionName`,
`versionCode` и непустым `apkUrl`. Покажи человеку эти строки — не пересказ.

## Что ломается чаще всего

| Симптом в логе | Причина и что делать |
|---|---|
| `versionName в APK (…) не совпадает с тегом` | поправь `versionName` в `app/build.gradle.kts` и сделай новый тег |
| витрина ответила `409` | `versionCode` уже опубликован — подними и перевыпусти |
| `APK подписан debug-ключом` | не подхватились `KEYSTORE_*`: проверь имена secret'ов |
| `не заданы secrets STORE_API и PUBLISH_TOKEN` | шаг 4 не выполнен |
| `Capture screenshots` красный | шаг помечен `continue-on-error`, релиз не страдает: скриншотов просто не будет |
| в карточке нет иконки | нет `store/icon.png` либо путь отличается от `ICON_PATH` в workflow |

## Что происходит дальше само

- **Скриншоты.** На шаге «Capture screenshots» поднимается эмулятор, ставится
  собранный APK, и `tools/screenshots.sh` сам обходит экраны: читает дерево
  через uiautomator, прокручивает списки, жмёт кнопки, тянет широкие элементы
  (так проходятся слайдеры). Кадры уезжают ассетами в релиз, ссылки — в витрину.
  Сценарии писать не нужно.
- **Иконка.** Если публикуешь готовый APK через панель, а не конвейером, иконку
  панель достаёт из пакета сама — включая случай, когда растровой иконки внутри
  нет и есть только векторный adaptive icon.
- **Уведомление об обновлении.** Магазин на телефоне проверяет витрину через
  15 минут после запуска и дальше раз в час.

## Приложение без исходников

Если есть только собранный APK, конвейеру нечего собирать. Тогда либо панель
магазина (загрузка APK в браузере), либо `tools/publish-apk.sh` — см. README
release-kit. Ограничение: следующие версии обязаны быть подписаны тем же
ключом, иначе обновление поверх не встанет.
